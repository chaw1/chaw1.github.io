CASE A · BATCH PIPELINE

万级任务提交，从超时到 0.89 秒；
重试 280 次，只产出 1 个版本。10k-task submission: from timing out to 0.89 s.
280 retries, exactly one version.

>2 min0.89 s内网LAB
问题Problem
客户一次提交上万文件，提交超时超过两分钟；任务执行结束后，产物仍可能没有登记、建版或对用户可见。Submitting 10,000 files timed out after two minutes, while completed computation could still leave outputs unregistered, unversioned or invisible.
我的职责My contribution
亲自完成早期 Worker 与批处理实现，后续负责架构、优化方案和故障注入验收，流水线增强由协作实现。I implemented the early worker and batch processing, then owned architecture, optimization planning and fault-injection acceptance, with later enhancements implemented collaboratively.
关键决策Key decision
队列与任务状态放进同一 MySQL 事务，结合并发领取、租约及幂等；把产物可读、版本落账和血缘闭合纳入交付状态。I kept queue entries and task state in one MySQL transaction, combined claims, leases and idempotency, and made readable outputs, version records and lineage prerequisites for delivery.
结果与边界Results and limits
LAB：万级提交降至0.89秒，280次重试仅一个版本；GPU采样仍有一次瞬时越限，万级端到端吞吐未完成验证。LAB: 10k-task submission fell to 0.89 s and 280 retries produced one version. GPU sampling still caught one transient overshoot; full 10k-task throughput was not verified.
展开技术细节与验证Read the technical detail & validation
  1. 取舍Decision

    选 MySQL 队列：FOR UPDATE SKIP LOCKED 并发领取，Redis 做心跳与 GPU 限流，outbox 发事件。队列可查、可修，不会出现“消息发了、状态没写”的双写不一致。再把“执行完成 ≠ 交付完成”写成状态机：产物可读、版本落账、血缘闭合才算 READY。I kept it in MySQL: concurrent claiming with FOR UPDATE SKIP LOCKED, Redis for heartbeats and GPU throttling, an outbox for events. The queue stays queryable and repairable, with no dual-write gap between message and state. Then I made "executed ≠ delivered" a state machine: READY only when the artifact is readable, the version recorded and the lineage closed.

  2. 验证Proof

    验收坚持故障注入，不只看吞吐：以“任务 + 文件”为幂等键，280 次重试只产出 1 个数据集版本。GPU 限流 3 Worker 并跑，Redis 采样 1,383 次仅 1 次瞬时越限。Acceptance required fault injection, not just throughput: with task + file as the idempotency key, 280 retries produced exactly one dataset version. Under GPU throttling with three workers, 1,383 Redis samples showed a single momentary overshoot.

约束与考虑过的方案Constraint and the options considered
  1. 约束Constraint

    客户一次提交上万文件，前端提交超过 2 分钟超时。更隐蔽的是“跑完了”和“能用了”之间有五个静默失败点：产物没保存、没登记、没建版本、没导入、前端看不见，都不报错。Customers submit 10k+ files at once, and submission timed out after two minutes. Worse, between "finished" and "usable" sat five silent failure points (not saved, not registered, not versioned, not imported, not visible), and none of them raised an error.

  2. 方案Options

    引入独立 MQ（Kafka / RabbitMQ），或把队列放进 MySQL，与任务状态同一个事务。Add a dedicated broker (Kafka / RabbitMQ), or keep the queue in MySQL in the same transaction as task state.

CASE B · DATA INGEST

客户的 9.9 GB 压缩包被网关砍断。
三次架构迭代后，生产零中断直传。A customer's 9.9 GB archive was cut off at the gateway.
Three iterations later: uninterrupted direct upload in production.

41.8MiB/s生产PROD
问题Problem
大压缩包经后端代理上传会被网关超时切断；分片传完也不代表导入成功，还需核对完整性和版本可追溯性。Gateway timeouts interrupted large proxied uploads. Receiving every part was not enough: imports also needed completeness checks and traceable versions.
我的职责My contribution
亲自推进存储与版本集成、直传迭代及上传事故修复；后续 Ingest／Upload V2 负责方案和验收，与团队协作实现。I implemented storage and version integration, iterated direct uploads and fixed upload failures; for later Ingest and Upload V2 work, I owned design and acceptance with collaborative implementation.
关键决策Key decision
浏览器按预签名分片直传对象存储，完成时由服务端核对片数与字节；以重试、检查点和版本血缘支持失败恢复。The browser uploads signed parts directly to object storage; the server checks part counts and bytes before completion, with retries, checkpoints and version lineage supporting recovery.
结果与边界Results and limits
生产直传验收：约10GB、237秒、41.8MiB/s，缺片请求被拒；真实1TiB与完整故障组合尚未验证，不代表Upload V2全量验收。Production direct-upload test: about 10 GB in 237 s at 41.8 MiB/s; missing parts were rejected. Real 1 TiB and full fault combinations remained untested; this was not complete Upload V2 acceptance.
展开技术细节与验证Read the technical detail & validation
  1. 取舍Decision

    采用对象存储原生 SDK 重签、浏览器直传。每个分片签一个 URL，直传到固定编号的 staging key；直传失败可按片回退到后端代理，两条路写同一个 key。complete 不信会话记录，直接列目录核对片数与总字节，缺片就拒。解压侧给每次 staging 写入包上应用层退避重试，把瞬断当成可重试。Re-sign with the object store's native SDK and upload straight from the browser. One presigned URL per part, written to a fixed, numbered staging key; a failed part can fall back to the proxy and both paths write the same key. Completion ignores session records and lists the prefix to check part count and total bytes, rejecting any gap. On extraction, every staging write gets application-level retry with backoff, so transient drops are retryable.

  2. 验证Proof

    生产验收：约 10 GB 测试包，310 个分片，237 秒，41.8 MiB/s，零中断；故意缺一片（309/310）时服务端拒绝。30 GB 合成包 480/480 文件、内存峰值 1.5 GB。生产血缘事件回填 18,370 条，六类对账全等。真实 1 TiB 与完整故障组合未跑完，方案里如实写明。Production acceptance: a ~10 GB package, 310 parts, 237 s, 41.8 MiB/s, no interruptions; with one part deliberately missing (309/310) the server refused. A 30 GB synthetic package landed 480/480 files at 1.5 GB peak memory. Backfilling lineage in production produced 18,370 events, with all six reconciliations exact. A real 1 TiB run and the full fault matrix were not finished, and the design document says so.

约束与考虑过的方案Constraint and the options considered
  1. 约束Constraint

    客户一次导入几 GB 到几百 GB 的图像、视频、点云压缩包，要求能进、失败能恢复、能追溯版本，且新版本不能破坏历史数据。经后端代理上传时，网关 60 秒超时直接掐断慢客户端。Customers import archives from a few GB to hundreds of GB. Uploads have to land, resume after failure, trace back to a version and never damage history. Proxied through the backend, slow clients were cut off by the gateway's 60-second timeout.

  2. 方案Options

    ① 网关代理上传：被超时掐断。② LakeFS 原生预签名：签名与地域绑定，跨环境不可用。③ 后端用对象存储原生 SDK 重签，浏览器直传。(1) Proxy through the gateway: cut off by timeouts. (2) LakeFS native presigning: signatures bound to a region, unusable across environments. (3) Re-sign with the object store's native SDK and upload straight from the browser.

快 9.4 倍，还避开了一个许可证陷阱。Segmentation without a GPU in the cloud:
9.4× faster, and a license trap avoided.

问题Problem
无GPU环境仍需交互式分割；原方案文字提示失效，单看速度或模型自评分无法发现质量、内存与许可证问题。Interactive segmentation had to run without a GPU. Broken text prompts showed that speed and model confidence alone could miss quality, memory and licensing problems.
我的职责My contribution
亲自定位文字提示失效根因、比较CPU分割选型与许可证边界，并处理内存上限；模型服务本体与算法同事协作完成。I diagnosed the broken text-prompt path, compared CPU segmentation options and license constraints, and addressed memory limits, collaborating with algorithm engineers on model services.
关键决策Key decision
选择 EfficientViT-SAM，用实际掩码质量、延迟、线程与内存测试做判断；否决质量退化的INT8方案，核查实际许可证。I selected EfficientViT-SAM using measured masks, latency, thread counts and memory, rejected the degraded INT8 option, and checked actual license files.
结果与边界Results and limits
LAB云上4核真机：同图分割6000→640毫秒，4K图峰值内存4078→1907MB；这些测试不代表所有图像质量与生产性能。LAB on a four-core cloud host: same-image segmentation fell from 6,000 to 640 ms; peak memory for a 4K image fell from 4,078 to 1,907 MB. These tests do not establish quality or production performance for all inputs.
展开技术细节与验证Read the technical detail & validation
  1. 取舍Decision

    换 EfficientViT-SAM。三条理由：质量上 FastSAM 不是检测器，CLIP 只能重排；速度上 9.4 倍；许可证上 README 写 Apache、LICENSE 文件实为 AGPL，私有化分发会触发 copyleft。INT8 被否决：只快 1.7 倍，mask IoU 掉到 0.42，而模型自估 IoU 不变，坏了也察觉不到。命名也守纪律：CPU 版不借用 SAM 3 的名字，不做虚假能力声明。EfficientViT-SAM, for three reasons: quality, since FastSAM is not a detector and CLIP can only re-rank; speed, at 9.4×; and licensing, since the README says Apache but the LICENSE file is AGPL, so shipping it on-prem would trigger copyleft. INT8 was rejected: only 1.7× faster, mask IoU fell to 0.42 while the model's self-estimated IoU stayed the same, so failure would be invisible. Naming stays honest too: the CPU service does not borrow the SAM 3 name.

  2. 验证Proof

    云上 4 核真机：6,000 ms → 640 ms；ORT 换 OpenVINO 后编码器 470 → 93 ms；线程数 2 → 4 为最优。另修一次 OOM：4K 图峰值内存 4,078 MB → 1,907 MB。On a real 4-core cloud VM: 6,000 ms → 640 ms; ORT to OpenVINO took the encoder from 470 to 93 ms; four threads was the sweet spot. A related OOM fix cut 4K-image peak memory from 4,078 MB to 1,907 MB.

约束与考虑过的方案Constraint and the options considered
  1. 约束Constraint

    云上环境只有 CPU，交互式标注需要亚秒级分割。现有 FastSAM 的“文字提示分割”自上线起就没生效过：输入 person,rider,car 和 banana 返回的框完全一样，根因是异常被静默吞掉。The cloud environment is CPU-only, and interactive labeling needs sub-second segmentation. The existing FastSAM text-prompt mode had never worked: person,rider,car and banana returned identical boxes, because an exception was silently swallowed.

  2. 方案Options

    修 FastSAM + CLIP；做 INT8 量化；换 EfficientViT-SAM-L0。Fix FastSAM + CLIP, quantize to INT8, or switch to EfficientViT-SAM-L0.

展开技术细节与验证Read the technical detail & validation
  1. 取舍Decision

    冻结六个仓的基线 SHA，先在与客户同款 OS 的鲲鹏实机上真装。验证机 16 核全绿，到了客户现场的 32 核机器上，三个 Python 服务重启 60+ 次：OpenBLAS / OMP 按核数起线程，撞上 nproc 上限。于是给所有算力容器钉死线程数，并把“验证机与客户机同规格，核数也要对齐”写进规范。我的判断规则是：同类组件里只有一个配了某参数，往往是过去事故的遗迹，应推广到全部。Froze the baseline SHA of six repositories and did a real install on a Kunpeng machine running the customer's OS. The 16-core test machine was all green; on the customer's 32-core machine three Python services restarted 60+ times, because OpenBLAS / OMP start a thread per core and hit the nproc limit. So every compute container got pinned thread counts, and "the test machine matches the customer's, core count included" became a team rule. My rule of thumb: when only one of a family of components sets a parameter, it is usually the scar of an old incident, and should be applied to all of them.

  2. 验证Proof
