    CASE A · BATCH PIPELINE

    万级任务提交，从超时到 0.89 秒；
    重试 280 次，只产出 1 个版本。    10k-task submission: from timing out to 0.89 s.
    280 retries, exactly one version.

    >2 min0.89 s内网LAB
    1. 约束Constraint

      客户一次提交上万文件，前端提交超过 2 分钟超时。更隐蔽的是“跑完了”和“能用了”之间有五个静默失败点：产物没保存、没登记、没建版本、没导入、前端看不见，都不报错。Customers submit 10k+ files at once, and submission timed out after two minutes. Worse, between "finished" and "usable" sat five silent failure points (not saved, not registered, not versioned, not imported, not visible), and none of them raised an error.

    2. 方案Options

      引入独立 MQ（Kafka / RabbitMQ），或把队列放进 MySQL，与任务状态同一个事务。Add a dedicated broker (Kafka / RabbitMQ), or keep the queue in MySQL in the same transaction as task state.

    3. 取舍Decision

      选 MySQL 队列：FOR UPDATE SKIP LOCKED 并发领取，Redis 做心跳与 GPU 限流，outbox 发事件。队列可查、可修，不会出现“消息发了、状态没写”的双写不一致。再把“执行完成 ≠ 交付完成”写成状态机：产物可读、版本落账、血缘闭合才算 READY。I kept it in MySQL: concurrent claiming with FOR UPDATE SKIP LOCKED, Redis for heartbeats and GPU throttling, an outbox for events. The queue stays queryable and repairable, with no dual-write gap between message and state. Then I made "executed ≠ delivered" a state machine: READY only when the artifact is readable, the version recorded and the lineage closed.

    4. 验证Proof

      验收坚持故障注入，不只看吞吐：以“任务 + 文件”为幂等键，280 次重试只产出 1 个数据集版本。GPU 限流 3 Worker 并跑，Redis 采样 1,383 次仅 1 次瞬时越限。Acceptance required fault injection, not just throughput: with task + file as the idempotency key, 280 retries produced exactly one dataset version. Under GPU throttling with three workers, 1,383 Redis samples showed a single momentary overshoot.

    CASE B · DATA INGEST

    客户的 9.9 GB 压缩包被网关砍断。
    三次架构迭代后，生产零中断直传。    A customer's 9.9 GB archive was cut off at the gateway.
    Three iterations later: uninterrupted direct upload in production.

    41.8MiB/s生产PROD
    1. 约束Constraint

      客户一次导入几 GB 到几百 GB 的图像、视频、点云压缩包，要求能进、失败能恢复、能追溯版本，且新版本不能破坏历史数据。经后端代理上传时，网关 60 秒超时直接掐断慢客户端。Customers import archives from a few GB to hundreds of GB. Uploads have to land, resume after failure, trace back to a version and never damage history. Proxied through the backend, slow clients were cut off by the gateway's 60-second timeout.

    2. 方案Options

      ① 网关代理上传：被超时掐断。② LakeFS 原生预签名：签名与地域绑定，跨环境不可用。③ 后端用对象存储原生 SDK 重签，浏览器直传。(1) Proxy through the gateway: cut off by timeouts. (2) LakeFS native presigning: signatures bound to a region, unusable across environments. (3) Re-sign with the object store's native SDK and upload straight from the browser.

    3. 取舍Decision

      选 ③。每个分片签一个 URL，直传到固定编号的 staging key；直传失败可按片回退到后端代理，两条路写同一个 key。complete 不信会话记录，直接列目录核对片数与总字节，缺片就拒。解压侧给每次 staging 写入包上应用层退避重试，把瞬断当成可重试。Option 3. One presigned URL per part, written to a fixed, numbered staging key; a failed part can fall back to the proxy and both paths write the same key. Completion ignores session records and lists the prefix to check part count and total bytes, rejecting any gap. On extraction, every staging write gets application-level retry with backoff, so transient drops are retryable.

    4. 验证Proof

      生产验收：约 9.9 GiB 测试包，310 个分片，237 秒，41.8 MiB/s，零中断；故意缺一片（309/310）时服务端拒绝。30 GB 合成包 480/480 文件、内存峰值 1.5 GB。生产血缘事件回填 18,370 条，六类对账全等。真实 1 TiB 与完整故障组合未跑完，方案里如实写明。Production acceptance: a ~9.9 GiB package, 310 parts, 237 s, 41.8 MiB/s, no interruptions; with one part deliberately missing (309/310) the server refused. A 30 GB synthetic package landed 480/480 files at 1.5 GB peak memory. Backfilling lineage in production produced 18,370 events, with all six reconciliations exact. A real 1 TiB run and the full fault matrix were not finished, and the design document says so.

    让发布可重复、可回滚，
    让运维从查日志变成看告警。    Releases you can repeat and roll back.
    Operations run on alerts, not log-grepping.

    −84.9%日志量log volume生产PROD
    1. 约束Constraint

      2026-05 之前只有内网与客户线。要在云上建正式环境，同时维持离线交付、内网研发、云上生产三条线不漂移。Before May 2026 there were only internal and customer environments. I had to stand up production in the cloud while keeping offline delivery, internal development and cloud production from drifting apart.

    2. 方案Options

    3. 取舍Decision

      选单机 k3s，把单点风险写进方案而不是回避；Argo CD 先 apply-only 分批纳管，设五条硬停止条件。定下“CI 是唯一出图口”，回滚就是改一行镜像 tag。事故后固化：共享凭证一次性注入全量并重启全量，验证用 11 × 7 = 77 格全矩阵而不抽样。Single-node k3s, with the single point of failure written into the plan rather than hidden; Argo CD apply-only in batches behind five hard stop conditions. CI became the only source of images, so a rollback is a one-line tag change. After an incident I set two rules: when a shared credential changes, inject it everywhere and restart everything in one go; and verify the full 11 × 7 = 77-cell matrix instead of sampling.

    4. 验证Proof

      access log 从 1,313 万行降到 71.2 万行，告警有效覆盖 64/64。生产 15 天探针可用性 99.9975%，7 天 331 万真实请求；100 并发压测整体 p95 50 ms。在与生产同机同配置的预发环境做极限压测，定位 project 服务 CPU 打满，2 核扩到 6 核后 84 → 205 req/s，p95 2.6 s → 0.85 s。Access logs fell from 13.13 M to 0.712 M lines, with 64/64 effective alert coverage. A stress test in pre-production, on the same host and configuration, found the project service CPU-bound; going from 2 to 6 cores took it from 84 to 205 req/s and p95 from 2.6 s to 0.85 s.

    CASE D · MODEL SELECTION

    云上没有 GPU 的分割服务：
    快 9.4 倍，还避开了一个许可证陷阱。    Segmentation without a GPU in the cloud:
    9.4× faster, and a license trap avoided.

    6,000 ms640 ms内网LAB
    1. 约束Constraint

      云上环境只有 CPU，交互式标注需要亚秒级分割。现有 FastSAM 的“文字提示分割”自上线起就没生效过：输入 person,rider,car 和 banana 返回的框完全一样，根因是异常被静默吞掉。The cloud environment is CPU-only, and interactive labeling needs sub-second segmentation. The existing FastSAM text-prompt mode had never worked: person,rider,car and banana returned identical boxes, because an exception was silently swallowed.

    2. 方案Options

      修 FastSAM + CLIP；做 INT8 量化；换 EfficientViT-SAM-L0。Fix FastSAM + CLIP, quantize to INT8, or switch to EfficientViT-SAM-L0.

    3. 取舍Decision

      换 EfficientViT-SAM。三条理由：质量上 FastSAM 不是检测器，CLIP 只能重排；速度上 9.4 倍；许可证上 README 写 Apache、LICENSE 文件实为 AGPL，私有化分发会触发 copyleft。INT8 被否决：只快 1.7 倍，mask IoU 掉到 0.42，而模型自估 IoU 不变，坏了也察觉不到。命名也守纪律：CPU 版不借用 SAM 3 的名字，不做虚假能力声明。EfficientViT-SAM, for three reasons: quality, since FastSAM is not a detector and CLIP can only re-rank; speed, at 9.4×; and licensing, since the README says Apache but the LICENSE file is AGPL, so shipping it on-prem would trigger copyleft. INT8 was rejected: only 1.7× faster, mask IoU fell to 0.42 while the model's self-estimated IoU stayed the same, so failure would be invisible. Naming stays honest too: the CPU service does not borrow the SAM 3 name.

    4. 验证Proof

      云上 4 核真机：6,000 ms → 640 ms；ORT 换 OpenVINO 后编码器 470 → 93 ms；线程数 2 → 4 为最优。另修一次 OOM：4K 图峰值内存 4,078 MB → 1,907 MB。On a real 4-core cloud VM: 6,000 ms → 640 ms; ORT to OpenVINO took the encoder from 470 to 93 ms; four threads was the sweet spot. A related OOM fix cut 4K-image peak memory from 4,078 MB to 1,907 MB.

    CASE E · ON-PREM DELIVERY

    无外网、国产 CPU、国产 OS：
    27 个镜像的整套平台离线交付。    No internet, domestic CPU, domestic OS:
    the whole 27-image platform, delivered offline.

    19个问题，5 个致命，都在出包前issues, 5 fatal, caught before shipping验证机LAB
    1. 约束Constraint

      客户机房是鲲鹏 aarch64 + 麒麟 V10，完全离线。语法校验、架构核对、compose config 全部通过，也不代表能装起来。The customer's data center ran Kunpeng aarch64 on Kylin V10, fully air-gapped. Passing syntax checks, architecture checks and compose config doesn't mean it will install.

    2. 方案Options

      按清单打包直接发往现场，或先在与客户同规格的实机上真装一遍。Package against a checklist and ship, or first install for real on a machine matching the customer's spec.

    3. 取舍Decision

      冻结六个仓的基线 SHA，先在与客户同款 OS 的鲲鹏实机上真装。验证机 16 核全绿，到了客户现场的 32 核机器上，三个 Python 服务重启 60+ 次：OpenBLAS / OMP 按核数起线程，撞上 nproc 上限。于是给所有算力容器钉死线程数，并把“验证机与客户机同规格，核数也要对齐”写进规范。我的判断规则是：同类组件里只有一个配了某参数，往往是过去事故的遗迹，应推广到全部。Froze the baseline SHA of six repositories and did a real install on a Kunpeng machine running the customer's OS. The 16-core test machine was all green; on the customer's 32-core machine three Python services restarted 60+ times, because OpenBLAS / OMP start a thread per core and hit the nproc limit. So every compute container got pinned thread counts, and "the test machine matches the customer's, core count included" became a team rule. My rule of thumb: when only one of a family of components sets a parameter, it is usually the scar of an old incident, and should be applied to all of them.

    4. 验证Proof

      两轮真装累计发现 19 个问题、5 个致命，例如 Docker 自身二进制是 x86、Redis 在 ARM64 上拒启、端口避让脚本把 9 个端口分到同一个。补丁复查时搭仿真环境真跑 21 条异常路径断言；验证脚本本身也被验证过。现场 5 条反馈逐一定性：1 条是真实缺陷，出补丁修复；其余主要是客户浏览器版本过低。Two real installs surfaced 19 issues, 5 of them fatal: the Docker binary itself was x86, Redis refused to start on ARM64, a port-avoidance script mapped nine ports to one. Patch review ran 21 failure-path assertions in a simulated environment, and the verification scripts were themselves verified. Five field reports were each triaged: one genuine defect, patched; the rest came mostly from an outdated customer browser.

    04/ HOW I WORK

    用 AI 放大产出，
    但不采信任何自报结果。    AI multiplies the output.
    Nothing self-reported is trusted.

    我写规格与验收清单，让 Codex 实现，再独立复算、实测。这套方式支撑了能力平台、可观测、桌面端等多条线同时推进，而验收始终由我自己把关。I write the spec and the acceptance checklist, Codex implements, and I verify independently by recomputing and running it. This let several lines move at once, from the capability platform to observability and the desktop client, while acceptance stayed with me.

    1. 01规格Spec

      写清目标、边界与可证伪的验收条件，包括前端接线状态。Goals, boundaries and falsifiable acceptance criteria, including frontend wiring status.

    2. 02实现Build

      Codex 按任务包实现，可断点续跑；多条线并行。Codex implements from a task package, resumable from checkpoints; several lines in parallel.

    3. 03复算Recompute

      不看自报数字，用另一个数据源或另一条路径独立重算。Ignore self-reported numbers; recompute from another source or another path.

    4. 04门禁Gate

      把教训写进门禁。存量失败用棘轮锁住，清单只准变短。Turn lessons into gates. Existing failures are locked by a ratchet; the list may only shrink.
